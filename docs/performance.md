# CI and controlled performance validation (milestone 19)

Milestone 19 adds GitHub Actions validation and a reproducible, disposable
100-monitor benchmark. Monitoring observations are generated by real HTTP requests
through the existing PostgreSQL → Redis → Celery prefork execution path. The
benchmark never writes check results, health outcomes, or historical observations.

## CI coverage

[The workflow](../.github/workflows/ci.yml) runs on pushes and pull requests. Its
`checks` job installs the hashed Python development lock and `npm ci`, checks Ruff,
mypy, operation safeguards, frontend formatting/lint/types/tests, OpenAPI contract
drift, and the native Next.js build. Vitest is capped at two workers to bound
CPU/memory use on CI and shared hosts while preserving the existing timeouts.
The `stack` job builds the runtime and backend
test images, executes the complete backend suite with PostgreSQL, Redis, real
prefork workers and Mailpit, runs the scheduling/restart/backup-restore smoke,
checks Chromium against the built frontend container, and runs a 100-probe harness
smoke. The smoke is explicitly **not** the 10,000-probe performance gate.

A manual `workflow_dispatch` runs those jobs and then the full `performance` job.
It requires 100 distinct probed monitors, at least 10,000 completed real HTTP
probes, successful correctness checks, and removal of its disposable project.
Only the sanitized JSON report is uploaded, with a 14-day retention period.
Database dumps, environment files, email contents, browser traces, and raw service
logs are not uploaded. Nothing is published or deployed.

Actions are pinned to full commit SHAs verified against their official release
references. The token has `contents: read`; checkout does not persist credentials.
There are no repository secrets, privileged PR triggers, image pushes, deployment
credentials, or remote execution steps beyond the normal CI runner. Browser
binaries go into the runner workspace; the workflow uses its existing Chromium
system libraries without installing system packages. These choices
follow GitHub's [workflow security guidance](https://docs.github.com/en/actions/reference/security/secure-use).
The workflow has been validated locally; a successful GitHub-hosted run can only be
claimed after the repository owner publishes and runs it. No remote run was
triggered for this milestone.

## Reproduce locally

Use the existing Ubuntu project environment and Docker engine. No host service
installation is required. The project virtual environment supplies HTTPX for the
stack smoke; the benchmark launcher itself uses only Python's standard library.

```bash
python3 scripts/local_stack.py init
BUILDX_GIT_INFO=false docker compose --env-file .cache/compose.env build api frontend
BUILDX_GIT_INFO=false docker compose --env-file .cache/compose.env -f compose.yaml -f compose.test.yaml build backend-tests
.venv/bin/python scripts/benchmark.py --output .cache/performance-new-run.json
```

The output path must not exist. Omit `--output` to use a new randomly named
`.cache/devpulse-benchmark-<random>/report.json`. Default loopback ports are 23000
(frontend) and 28025 (Mailpit); override `--web-port` and `--mail-port` together if
needed. `--rounds 1` is a fast 100-probe harness check; the default is 100 rounds.
The launcher always creates a new Compose project, refuses an existing project,
uses the explicit test and benchmark overlays, and removes **only its own**
containers, networks and volumes in `finally`. It preserves sanitized evidence on
failure and will not overwrite an earlier report. Abrupt process/host termination
can prevent cleanup; use the printed project name to inspect and remove that
specific disposable project. Never use a development project's volume as a
benchmark target.

The mounted workload additionally refuses any non-test environment, database
other than `devpulse_test` at the private Compose `postgres` host, or database
containing accounts. Fixture scripts are absent from runtime images. The HTTP
fixture shares the probe worker's network namespace and uses the existing exact
`127.0.0.1:8081` test exception; the production destination policy is unchanged.

Build inputs are pinned: Python 3.13.15 and Node 24.21.0 image digests, PostgreSQL
18 and Redis image digests, Mailpit's image digest, hashed Python lockfiles and
`package-lock.json`. CI starts from a fresh runner and installs those locks.
Reports record image IDs and SHA-256 hashes of source and build inputs without
using repository metadata. This reproduces dependencies and build procedure;
it does not promise byte-identical Next.js build IDs, OCI metadata, or timing
across machines. Updating pins is an explicit maintenance change.

## Workload and measurement definitions

- Ten explicitly labeled, disposable verified fixture accounts own ten monitors
  each: 100 enabled monitors, within the existing per-account/global limits.
  Authentication uses the real login endpoint; credentials remain in memory.
- Every monitor requests the local fixture with GET, expecting HTTP 200. The
  response is a fixed 36-byte JSON body with a configured 10 ms delay. Health and
  statistics requests are excluded from its independent completed-response count.
- Each round makes the 100 fixture configurations due **now**, invokes the actual
  bounded dispatcher four times (25 reservations per call), and waits for all 100
  scheduled runs to finish. The normal Beat also remains running. Stored intervals
  are 86,400 seconds, so it cannot introduce another normal interval within the
  test. No timestamp is backdated and no production scheduling interval is changed.
- Workers use the normal two-process prefork pool, prefetch one, late acknowledgments,
  fenced leases and PostgreSQL finalization. Redis remains only the broker. There
  is no eager task mode, replacement probe transport, or in-memory persistence.
- The full gate requires 10,000 HTTP 200 checks, 10,000 independent fixture response
  writes, 100 distinct monitors, one attempt per successful run, no unexpected
  terminal outcomes, and HTTP 200 for every sampled API request. A smaller smoke
  can pass its correctness checks while `milestone_19_volume_met` remains false.
- One authenticated client cycles through dashboard, monitor list, monitor
  analytics, check history and incidents through the frontend `/api/v1` proxy.
  It waits 250 ms after each response, with one request in flight. Timings include
  the proxy, authentication, database work, and complete response read. Routes are
  preflighted once before measurement. Reported p50/p95 use nearest-rank percentiles
  across the measured samples; this is not a saturated API load test.
- Queue lag is the first persisted attempt's `started_at` minus its run's
  `scheduled_at`. It includes publication, broker waiting and lease acquisition;
  it is not Redis-only wait time. Probe duration is the existing persisted duration.
- Elapsed workload time includes dispatch and round draining, excluding container
  startup, fixture seeding/login and final evidence collection. Throughput divides
  completed probes by that measured duration.
- PostgreSQL evidence includes row counts, migration head, database size growth,
  `pg_stat_database` counter deltas, sampled connections/active connections and
  pending-or-running runs, plus a real `EXPLAIN (ANALYZE, BUFFERS)` of recent-check
  retrieval after the workload. Polling is every 250 ms while draining a round;
  sampling pauses during dispatch, so sampled peaks are lower bounds. Statistics
  include API traffic, Beat, health probes and the harness itself. Transaction
  rollbacks include ordinary read-session cleanup and are not an error count.

## Interpretation limits

This is a local, all-success, accelerated burst workload against one loopback
fixture. It does not measure external DNS/TLS/network variation, a normal one-minute
schedule, sustained production capacity, noisy neighbors, multi-worker-host
scaling, user concurrency, long-retention volumes, failure storms, or an SLA.
Failure/retry, lease fencing, isolation, and broker/database recovery remain
covered by separate real worker/integration and stack smoke tests. The synthetic
fixture accounts and measurements are not customer history or public-demo data.
No performance latency threshold is invented: this milestone gates correctness
and volume and records the measured distributions for later comparisons.

## Saved evidence — 2026-09-30

[The full JSON report](evidence/m19-performance-2026-09-30.json) records the actual
run, including image IDs, source hashes and the database query plan.
[Runtime/hardware details](evidence/m19-runtime-2026-09-30.json) were read from the
running services during the same workload. The report's `versions.redis` is the
Python Redis client (6.4.0); the server was Redis 7.4.11.

The run completed **10,000 real HTTP probes across 100 monitors** in **791.894
seconds** (13 minutes 11.894 seconds), averaging **12.628 probes/second**. All
10,000 scheduled runs succeeded on one attempt; the fixture independently counted
10,000 completed HTTP responses. There were zero probe errors and all **2,783**
measured API responses were HTTP 200. This is controlled benchmark evidence,
not availability history or a production capacity claim.

| Authenticated API route | Samples | p50 ms | p95 ms | Maximum ms |
| --- | ---: | ---: | ---: | ---: |
| Dashboard | 557 | 39.413 | 60.798 | 1508.132 |
| Monitor list | 557 | 23.357 | 37.236 | 426.573 |
| Monitor analytics | 557 | 36.367 | 56.610 | 1556.716 |
| Check history | 556 | 28.665 | 44.706 | 460.513 |
| Incidents | 556 | 23.131 | 37.431 | 483.533 |

The long-tail maxima are retained; low p95 values do not imply every request was
fast. Queue lag p50/p95/max was **3185.534 / 6009.818 / 8845.391 ms**. Persisted
probe duration p50/p95/max was **64.329 / 91.321 / 215.375 ms**. The 10 ms fixture
sleep is only one part of measured probe duration.

PostgreSQL finished with 100 monitors, 10,000 runs and 10,000 checks, no incidents,
and migration `f16b4d8e302a`. Database size grew from **8,689,343 to 14,775,999
bytes**. Sampled peaks were 7 connections, 4 active connections and 80 pending or
running runs. Counter deltas included zero deadlocks, zero conflicts, zero
temporary files/bytes, 73 blocks read and 15,426,733 block hits. The recent-check
query plan took 0.204 ms planning and 4.888 ms execution after the run. These are
small warm local-data measurements, not a long-retention query capacity result.

The Ubuntu 24.04 WSL2 client used kernel `6.6.87.2-microsoft-standard-WSL2` on a
13th Gen Intel Core i7-1355U. Docker Desktop 29.2.0 reported x86_64, 12 logical CPUs
and 8,163,377,152 bytes of available engine memory; containers had no individual
resource limits. Runtime versions were Python 3.13.15, Node 24.21.0, PostgreSQL
18.6, Redis 7.4.11, Celery 5.6.3, SQLAlchemy 2.0.54, HTTPX 0.28.1 and Mailpit 1.31.2.
The host was shared with existing local services and light editing/static checks;
heavy builds and test suites ran after the timed workload.

The full run's source hashes identify the measured code. Subsequently, the wrapper
was hardened to clear pass flags when its child exits unsuccessfully, even if the
child emitted a report first. That failure path has a regression test; the timed
workload and application code are unchanged. A short rerun validates the final
wrapper without treating its measurements as the full benchmark. Its
[100-probe evidence](evidence/m19-harness-smoke-2026-09-30.json) records
`milestone_19_volume_met: false`, as intended.

Reports contain allowlisted metadata, aggregate counts/timings, query-plan
structure, image IDs and file hashes. They omit request/response bodies, cookies,
tokens, passwords, target query strings, email messages and account/monitor IDs.

## Final local validation

[The validation record](evidence/m19-validation-2026-09-30.json) records:

- Fresh backend runtime, frontend runtime and backend test image builds with
  `--no-cache`, using the unchanged dependency locks.
- **317 backend tests passed**, no skips, against real PostgreSQL, Redis, Linux
  prefork workers and Mailpit; two existing Starlette/AnyIO deprecation warnings.
- **20 operation-safety tests passed**, including refusal to overwrite evidence or
  reuse existing projects, failure cleanup, child-exit status, percentile calculation
  and independent fixture counting.
- **107 frontend tests passed**, plus formatting, lint, strict types, API contract
  drift and the native production build. Three initial five-second timeouts under
  concurrent cold builds were resolved by bounding Vitest to two workers; test
  assertions and timeouts were preserved.
- **One real Chromium container workflow passed**, covering desktop/mobile layouts,
  images, anonymous API denial, the empty public demo and accessible form errors.
- **Ten real stack smoke checks passed**, including scheduling, retries/incidents,
  SMTP, worker/Redis/PostgreSQL outages, persistence and isolated backup/restore.
- Backend and operation-script Ruff/format checks passed; mypy passed all 67 app
  files. Project and runtime-image dependency consistency checks passed.
- Actionlint 1.7.12 accepted workflow syntax and expressions; optional ShellCheck
  and Pyflakes integrations were disabled. No GitHub-hosted workflow was executed.
- The full **10,000-probe** gate and the final wrapper's separate **100-probe** smoke
  passed. All disposable milestone 19 containers, networks and volumes were removed;
  pre-existing local services were left running.

Milestone 19 is complete. Milestone 20, publishing and deployment were not started.
